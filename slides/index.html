Next: the problem.

Agents now write and run their own code

Model-generated code is untrusted code, and today it often lands next to your production services.

Coding agents, data agents, research agents all do the same thing now: the model writes code and executes it to get an answer.

  • That code is untrusted by construction: nobody reviewed it, and the prompt that produced it may have come from a web page or a ticket.
  • In a plain cluster it runs as a container, which means on the kernel your production pods share. A kernel bug or a container escape is one hop from payments.

Next: the pattern the industry is converging on.

Separate reasoning from execution

The pattern that is emerging: an external control plane runs the loop, and the code runs in a sandbox you own, inside your own cluster, next to your data.

  • The managed-agent products do this. Open source frameworks do this. It is the right split.
  • But it moves the whole question to one place: the dashed line. Everything the agent can reach, it reaches from inside that box.

Next: what that line can be made of.

What the boundary can be made of

Four ways to draw the line, each a different boundary, not a ranking of good and bad.

  • Containers: namespaces and cgroups on one kernel. Great density, shared kernel.
  • Userspace kernel, gVisor: intercepts syscalls, so the node kernel sees fewer of them. Soft isolation.
  • VM, Kata: the pod gets its own guest kernel, run by a VMM on the node, on top of KVM. VM isolation.
  • Hardware-isolated microVM: same idea, own kernel, but the sandbox is a first-level guest of the Nitro hypervisor. CPU and memory isolation between sandboxes is enforced in hardware, with no nested virtualization.

This talk is about the fourth column: hardware-level isolation for every agent.

Next: what that looks like on a node.

Give every agent its own kernel

What changes is what sits between the kubelet and your containers.

  • From the outside it is still a pod: scheduled normally, a VPC IP, volumes through the same CSI drivers, kubectl exec, logs and port-forward all work.
  • Instead of starting the containers on the node kernel, containerd launches a Nitro sandbox for the pod: its own kernel, hardware-isolated CPU and memory, and it belongs to that pod alone.
  • Two agent sessions on one node: two sandboxes, two kernels. The regular pods next to them are untouched.

Next: what you type to get this.

Kubernetes-native: one line on a normal pod spec

No node selector, toleration or sidecar.

apiVersion: v1
kind: Pod
metadata:
  name: hello-sandbox
spec:
  # the only change:
  runtimeClassName: isolated-sandbox
  containers:
  - name: main
    image: amazonlinux:2023
    command: ["sleep", "infinity"]

Need no network at all? One annotation.

metadata:
  annotations:
    sandbox.amazonaws.com/network-isolated: "true"

The guest boots with loopback only.
kubectl exec and logs still work.

This is the whole opt-in. One line.

  • The RuntimeClass carries the scheduling constraints, so there is no node selector, no toleration, no sidecar. On EKS Auto Mode the node comes up on demand.
  • For code that must not talk to anything: one annotation, and the sandbox boots with no network device. Not filtered, absent. You can still exec in and read logs, because that goes over the sandbox's own channel.
  • Two classes: isolated-sandbox protects the node and the other pods from the pod. confidential-sandbox also treats the node as untrusted; Todd covers what that takes.

Next: how you know it worked.

Prove it from inside the pod

Regular pod

$ kubectl logs hello-default
/sys/class/dmi/id/product_name:  m8a.xlarge
disks:   dm-0 nvme0n1 nvme1n1 zram0

The EC2 instance it shares with every other pod.

Sandboxed pod

$ kubectl logs hello-sandbox
/sys/class/dmi/id/product_name:  m8i.enclave
disks:   dm-0 vda vdb vdc

$ kubectl logs hello-network-isolated
ipv4:    127.0.0.1
route:   none

Its own machine, virtio disks, and no way out. Ready in about 5 s.

Same image, same command, one line different. The pod's own logs are the evidence.

  • The regular pod reports the EC2 instance and its NVMe disks: it shares that machine with everything else on the node.
  • The sandboxed pod reports its own VM, m8i.enclave, and virtio block devices. Different kernel, different boot, different hardware view.
  • With the annotation: only loopback has an address and there is no route. There is no network device to misconfigure.
  • After the first node exists, a new sandboxed pod is Ready in about 5 to 6 seconds, most of it the guest booting.

Next: doing this at the scale of sessions, with agent-sandbox.

agent-sandbox: pods as sessions kubernetes-sigs

agent-sandbox is the Kubernetes SIG project for exactly this shape: a pod per session. A Nitro sandbox is a RuntimeClass on a pod template, so it works with it unchanged.

  • Put runtimeClassName in the SandboxTemplate.
  • A SandboxWarmPool keeps pods booted. A SandboxClaim per session adopts one: in our runs, Ready in 0.8 seconds, about what an ordinary pod takes. The pool refills in the background, off the path the user waits on.
  • A Sandbox is the stateful shape: a stable identity and a volume. Suspend it when idle, pay nothing for compute, resume with the workspace intact.

Size the pool to your peak claim rate, not to the number of sessions.

Next: what the agent can reach from inside.

Scoped egress, scoped credentials

The kernel boundary says what the agent cannot touch. These two say what it can reach.

  • Egress: a standard NetworkPolicy. It is enforced by eBPF on the host side of the pod's interface, which the guest has no access to, so nothing inside the sandbox can reconfigure it, whatever UID it runs as. On Auto Mode you can allow by hostname.
  • Credentials: EKS Pod Identity. The pod's ServiceAccount maps to one IAM role, scoped to the agent's job. Short-lived, served from the node, no keys baked into the image.
  • And when the task needs neither, the network-isolated annotation removes the device altogether.

Next: Todd, how this is built.

What sits under a RuntimeClass

Todd. Two machines on one slide, and the hypervisor under both.

  • Left, the parent instance: kubelet, containerd, and the sandbox-shim, the shim v2 binary the RuntimeClass handler points at. It drives firecracker, which presents virtio-vsock, blk and net to the parent kernel.
  • Right, the Nitro Sandbox: its own kernel, eks-sandbox-agent taking requests from the shim, and its own containerd running the workload. The images are unchanged.
  • Between them: the device data path is Device Memory Buffers, and lifecycle and runtime notifications cross through the Nitro Hypervisor. The two kernels never share memory mappings.

Kubernetes sees a pod. The handler is the only new word.

Next: the two files that wire it up.

Wiring a RuntimeClass to a shim

containerd: a handler and its shim

# /etc/containerd/config.toml
[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.microvm]
  runtime_type = "io.containerd.microvm.v2"
  # -> binary containerd-shim-microvm-v2 on PATH
  pod_annotations = ["sandbox.example.com/*"]
  # annotations the shim may read

Kubernetes: the class pods name

apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: isolated-sandbox
handler: microvm
overhead:
  podFixed: { memory: "160Mi", cpu: "250m" }
scheduling:
  nodeSelector:
    sandbox.example.com/capable: "true"

The class carries scheduling and overhead,
so the pod spec stays at one line.

Two files. Left is the node, right is the cluster.

  • In containerd, a runtime entry named microvm with a runtime_type. containerd turns io.containerd.microvm.v2 into a binary name, containerd-shim-microvm-v2, and starts it. pod_annotations is the allowlist of annotations the shim is handed, which is how network-isolated reaches the runtime.
  • In Kubernetes, a RuntimeClass whose handler is that name. It also carries the pod overhead the guest costs and a nodeSelector for capable nodes, which is why the pod needs no selector of its own.
  • Values here are illustrative; the shape is what matters.

Next: when the node itself is the adversary.

The confidential use case: the node is the adversary confidential-sandbox

When the data matters more than the node: regulated workloads, multi-tenant platforms, third-party clusters.

Todd. Isolated mode protects the node from the agent. Sometimes you need the reverse.

  • An agent handling customer records, source code or regulated data on a cluster you do not fully control: a shared platform team, a third-party provider, or a node someone may have compromised.
  • confidential-sandbox makes the sandbox the boundary. The node cannot read its memory or its disk, and cannot exec into it. The writable layer is encrypted inside the guest.
  • The node still holds the pod's credentials, so credentials alone protect nothing. KMS releases keys only to a guest that proves what it is running. The node, with the same credentials and no attestation, is refused.

Limits, said plainly: the node can still deny service, and this protects the data from the node, not from the workload's own code.

Next: the gap a kernel boundary alone leaves open.

The gap: the node still tells the guest what to run

A kernel of its own protects the node from the pod. It says nothing about the other direction.

  • Every request that shapes the workload comes from the node: which image, which args, which mounts, whether to exec a shell into it.
  • In isolated mode that is fine: the node is trusted. In a confidential setting, where the node operator or a compromised node is the adversary, the guest agent cannot just obey.
  • So the guest needs a policy that says what the workload owner intended, and a way to prove to the outside which policy it is running.

Next: the policy language.

Cedar: the policy the guest enforces CNCF Sandbox

permit(
  principal,
  action == Agent::Action::"CreateContainer",
  resource == Workload::Container::"main"
)
when {
  context.image_ref ==
    "public.ecr.aws/myapp@sha256:abc123..." &&
  context.image_signers.contains(
    "arn:aws:signer:...:my-team")
};

// nothing else is permitted: default deny

Generated by genpolicy from the manifest. Evaluated inside the guest.

Why Cedar

  • Open source, Rust, CNCF Sandbox
  • Default deny; forbid beats permit
  • Analyzable: ask what a policy allows
  • Fast enough for the request path

Cedar is an open source authorization language from AWS, now a CNCF Sandbox project.

  • This policy says: container main may be created only with this exact image digest, and only if the image carries a signature from this signing profile. Nothing else is permitted, because Cedar is default deny.
  • You do not write it by hand. genpolicy reads the manifest, resolves the tag to a digest, and emits the policy. It goes on the pod as an annotation and the guest agent evaluates it on every request: create, exec, logs, mounts.
  • It is analyzable: the language is designed so tools can answer "what does this policy allow" rather than just "did this request pass".

Next: two trust models on one mechanism.

Two trust models, one mechanism

isolated-sandboxconfidential-sandbox
Node istrusteduntrusted
Policyoptional, permissiverequired, default deny
Admissionany valid specimage digest, args, env, mounts pinned
Exec, stdinalloweddenied
Writable layerplainencrypted in the guest
SecretsPod Identityonly to an attested guest

Same shim, same VMM, same guest agent, same policy engine. Only the policy changes.

  • Isolated: the node is trusted. Policy is optional and permissive; exec and stats work as you expect; admission accepts any spec. This is what the agent demo used.
  • Confidential: the node is the adversary. The policy pins every admission field to a digest and a value, denies exec and stdin so the node cannot look in, encrypts the writable layer inside the guest, and secrets are released only to a guest that can prove what it runs.
  • That last row is the piece a policy alone cannot provide.

Next: closing the loop with attestation.

Closing the loop: a measured policy and an outside verifier

Measurement alone enforces nothing. The guest will run whatever policy the node hands it; it just records which one. The loop closes outside.

  • 1, 2: the owner generates the policy; the tool also prints the PCR17 the sandbox will measure it into, before anything runs.
  • 3, 4: inside, the agent enforces it and measures it. The Nitro Secure Module signs an attestation document carrying the PCRs.
  • 5, 6: the KMS key policy requires that exact PCR17 and the EKS service name on PCR8. A substituted policy means a different PCR17, so kms:Decrypt fails and the encrypted layers never open. Only the intended policy gets the key.

Any verifier that checks the attestation document works here. KMS is the one you already have.

Reference implementation: Nitro sandboxes on Amazon EKS

This is the shape we just walked through, as it ships on EKS.

  • The interfaces are the open ones: RuntimeClass, containerd and shim v2, OCI images, the OCI encryption spec, Notation signatures, Cedar.
  • The boundary is where the reference implementation differs from a software VMM on a node: the sandbox is a first-level guest of the Nitro hypervisor, the same hypervisor under every EC2 instance, so isolation between sandboxes is enforced in hardware with no nested virtualization.
  • Policy and image trust are evaluated inside the guest, and KMS is the outside verifier. Nothing on the node has to be trusted for a confidential pod.
  • And because it is a RuntimeClass, agent-sandbox and everything Carlos showed sits on top unchanged.
